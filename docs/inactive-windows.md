# Visible TUI startup without requested activation

Current default: core 1.3.4-rc.1 uses Windows Terminal (`ORCH_TUI=wt`) per user preference through a detached no-activate helper. The helper keeps the initiating foreground window in place during the short asynchronous WT startup guard, while leaving the TUI visible and interactive. The current observation is recorded in [1.3.1 focus evidence](../test/inactive-window-validation-1.3.1.json).

The helper creates the WT or fallback console with Windows `CreateProcessW`, `CREATE_NEW_CONSOLE` and `STARTF_USESHOWWINDOW/SW_SHOWNOACTIVATE`. It briefly restores the initiating foreground window during startup; typing alone does not cancel that guard while the initiating window remains foreground, while an input event accompanied by an actual focus switch is treated as an intentional user switch. The TUI remains a visible, interactive console, not headless, hidden or minimized. Only the short-lived process-creation helper is hidden. The launch preserves the initiating workspace and existing task/checkpoint/close behavior.

The PowerShell launch helper and the opt-in focus probe set both console and pipeline output to UTF-8 (`chcp 65001` plus explicit .NET encodings). This keeps Chinese paths, task prompts and diagnostics intact when the Windows locale uses a legacy code page.

`ORCH_TUI=wt` remains the default and keeps Windows Terminal's IME/TSF behavior. If Windows Terminal is unavailable, the same guarded helper uses the visible console fallback. Doctor reports `windowActivation: terminal-managed` for the WT path and `no-activate` for the fallback.

The controlled live probe uses a visible eight-second PowerShell job and monitors foreground notifications, actual foreground samples, visibility, minimized state, execution receipt and automatic closure. The current WT observation passed: the window was visible, not minimized and automatically closed; it had zero target foreground samples and zero notifications whose actual foreground was the target. One notification named the target window while the initiating window remained the actual foreground, which is retained for diagnosis. This is a host-level focus observation, not a universal OS guarantee.

For the continuous-input acceptance gate, run `powershell.exe -NoProfile -File test/live-inactive-window.ps1 -Workspace <workspace> -ContinuousInput`. This opt-in mode creates a temporary, owned WinForms initiator window and sends harmless synthetic period keystrokes while the visible TUI starts. The JSON report records `inputAttempts`, `inputDelivered`, `inputLostFocus`, and `inputError`; acceptance requires input delivery with no observed focus loss. The current-core result is preserved in [1.3.4 continuous-input evidence](../test/inactive-window-validation-1.3.4-rc.1.json). It never types into the user's existing application. Do not run this probe while unsaved work depends on the current foreground window. If Windows Forms, an interactive desktop, or the visible terminal is unavailable, retain the diagnostic output and mark the gate skipped; do not treat the ordinary startup probe as continuous-input evidence.

Run `powershell.exe -NoProfile -File test/live-inactive-window.ps1 -Workspace <workspace> -Legacy` for an opt-in visible direct-console probe. Do not click or minimize its window during the observation. Windows or another application may still activate a window; the plugin requests non-activation and cannot promise that all external focus changes are prevented. Runtime argument and helper-failure regressions run with the normal test suite. See [current validation evidence](../test/inactive-window-validation-1.3.1.json) and [historical observations](../test/inactive-window-validation.json) for recorded results and limitations.
