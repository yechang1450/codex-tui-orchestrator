# Network response-loss recovery validation (historical 1.2.3 record)

The historical 1.2.3 record has controlled integration coverage for two ambiguous network outcomes. A real Node worker in a Windows PowerShell process sends a POST to a temporary HTTP server listening only on `127.0.0.1`. The server records a side effect, then either destroys the response connection or withholds the response until the client's 500 ms deadline expires. No external service, account or machine network configuration is changed.

Both cases assert the actual transport error (`TypeError` for connection loss and `TimeoutError` for the response deadline), one server-side effect, one execution attempt and a durable `needs-reconciliation` task status. Resume must preserve that status without another request or launcher. The test then supplies an independent check of the server-side result, verifies the existing run and resumes it again: success requires the effect count and attempt count to remain one. The earlier completed task must also remain executed once.

The tests reuse the existing real-process recovery harness in `test/recovery-runtime.test.mjs`. They supplement its explicitly retry-safe process-failure scenario. Runtime code, release manifest and core hash are unchanged, so the [current eight-window and controller-crash evidence](live-validation-1.2.3.md) still refers to the same executable core. Final regression counts are recorded in [machine-readable evidence](../test/network-recovery-1.2.3.json).

This verifies handling of uncertain task-side effects after a lost response. It does not emulate the Codex provider protocol, its internal reconnection behavior, prolonged poor connectivity or an operating-system reboot. It is not a claim that arbitrary remote operations execute exactly once. Unproven side effects still require reconciliation, not an automatic retry-safe override. Historical 1.3.1 evidence is tracked separately in [network and reboot validation](network-reboot-validation.md).
