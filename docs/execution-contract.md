# Dedicated execution contract (core 1.4.4-rc.1, run protocol 2)

The dedicated Codex plugin uses a physical release snapshot of scripts/core and verifies release.json at startup. Changes are promoted only after verification. This repository accepts Codex only.

> **Maintainer reference.** This is the detailed sealed-runtime and recovery
> contract, not an installation or daily-use guide. Start with the
> [README](../README.md) for ordinary use. Its defense-in-depth descriptions do
> not make task prompts a supported channel for secrets.

## Planning and capacity

Environment preparation precedes task execution. The native PowerShell bootstrap can provision verified Node/npm, the locked SDK and the fixed native CLI without making a model request. A trusted SessionStart hook invokes the same preparation; plugin installation alone does not grant host hook trust. Runtime data ownership, bounded preparation and explicit failure behavior are defined in [environment setup](environment-setup.md). The bootstrap preparation deadline never becomes the execution deadline for a long task.

Concurrency is governed by a runtime memory budget (`ORCH_CAPACITY_MODE=dynamic`): planning preserves every atomic task and only groups dependency, conflict or unknown-scope components into serial blocks. Blocks with no cross-block dependency or resource conflict remain independent. If the result has one block, the initiating conversation executes it directly. Before orchestration, available memory at or below 1000 MB returns inline. Before every launch, the coordinator atomically reads available memory and reserves the block's predicted peak plus existing unconsumed reservations. A block starts only when the predicted peak remains strictly below available memory minus the mandatory 1000 MB reserve. A block that does not fit is deferred and rechecked after a running block releases its lease; there is no merge-to-fit and no hard-run escape. Every window uses the rolling observed cost (default 400 MB, with declared task memory added once per serial block); observed peaks above 800 MB are retained. Each block starts as soon as its own prerequisites are verified and a memory/resource lease is available. A dependent of A does not wait for unrelated B. Reject unknown, self and cyclic dependencies before launching. Merge transitive resource conflicts and preserve dependency order. Windows file locks normalize case, separators and existing junction ancestors, and account for directory containment.

The predicted peak is an estimate from prior observations and declared task costs. An unexpected task can exceed it; the 1000 MB reserve is a scheduling rule, not a mathematical guarantee that the machine cannot run out of memory.

The parent persists a public manifest with a credential-redacted request, the structured TodoList and T001... task identities before asking the planner. When the original recovery fields contain credential-shaped text, they are kept only in a controller-owned CurrentUser-DPAPI record bound to the workspace, run and public projection; a missing or mismatched private record makes recovery refuse. Model already_done/feasible flags never authorize omission. Uncertain model coverage falls back to the complete original inventory in a serial block. Each block receives the global TodoList plus its current block view.

Task parsing preserves ordinary comma continuations and quoted command separators. Deterministic planning uses the same boundaries as the original ledger. Semantic classification must return the original IDs; the parent restores original text by ID before grouping. A paraphrased summary cannot silently collapse otherwise valid parallel work into the coverage fallback. Credential-shaped requests never cross the decomposition-cache boundary: the cache does not read, write, repair, evict, or migrate them.

## Execution and verification

The initiating agent chooses a unique run ID and defines independent acceptance checks before launch. This is automatic parent preparation, not a user approval prompt.

Global CLI options precede the free-form execution request. Option-like words after the request begins remain task text. Commands that take a run ID, such as `--verify-run`, also accept their options after that ID. JSON acceptance compares nested object contents structurally, so object key order does not change the result; array order and actual values still matter.

- Execute: node <absolute-entry> --run-id <id> --acceptance-file <absolute-json> --exec <request>
- Poll: node <absolute-scripts>/poll-windows.mjs --run-id <id> --require-all-success
- Recheck outputs without rerunning tasks: node <absolute-entry> --verify-run <id> --acceptance-file <absolute-json>
- Recover the saved plan after interruption: node <absolute-entry> --resume-run <id>

Capacity retries require a structured provider error. A user prompt, tool result, final answer or unstructured stderr containing an overload phrase is not permission to replay work. A completed checkpoint with independently verified output remains successful even if the provider subsequently reports overload. A started task with an unproven result keeps `needs-reconciliation` in task status when its execution block times out or exhausts retries.

Recoverable reconnect notifications do not invalidate a later successful `turn.completed` and zero CLI exit. A terminal `turn.failed`, invalid stream, nonzero exit or cancellation still fails execution. Completed tasks without parent checks keep `awaiting-verification`; neither network recovery nor capacity handling supplies missing acceptance conditions.

A known failed CLI exit is published as `failed`, not as a polling timeout. The planner and both execution modes inherit the latest structured settings of the initiating Codex turn: model, reasoning effort and service tier. Native `CODEX_HOME/config.toml` fills missing turn fields; `ORCH_MODEL`, `ORCH_EFFORT` and `ORCH_SERVICE_TIER` are fallback values only when no initiating or native value exists.

Visible watchdog self-close is an execution exit rather than a timeout; it still requires independent task verification. The settings snapshot is applied to every visible and headless worker before launch, so a worker cannot silently select another model or reasoning level. They inherit the configured model provider and credentials by default, including third-party providers configured in CODEX_HOME. `ORCH_PROVIDER=openai-https` selects the hardened OpenAI-authenticated HTTPS Responses provider instead; a configured `ORCH_OPENAI_BASE_URL` (or legacy `ORCH_STEADY_RELAY_BASE_URL`) implies that mode and is normalized and passed to the planner and the visible/headless workers alike. An explicit `ORCH_PROVIDER=inherit` keeps inheritance even when a relay URL is set, and any other value fails closed.

Each run owns workspace/temp/orchestrator/runs/<id>/{manifest.json,summary.json,acceptance.json,attempts/,verification-report.jsonl}. These workspace-readable ledgers, status events, verification reports, and auxiliary spawn/self-test reports use the credential-redacted public projection. Every attempt records its exact remaining task IDs and a unique token. The TUI runs the supplied checkpoint command before and immediately after each task. The start record is created exclusively; a duplicate start fails. Poll requires the exact run ID, every planned block, every original task, verified statuses and closed launcher identities. An unrelated or previous run never satisfies this check. Failed prerequisites block dependants and remain in the task ledger. After a worker exits and its owned process is proven gone, its block enters one FIFO verification queue; verification never runs concurrently and never inspects live blocks. A completion marker or window closure alone is not success. Missing acceptance checks produce awaiting-verification, never a false pass. The parent can supply checks and recheck the same run without another TUI execution. If `summary.json` is absent, status may expose a planning-only manifest as an unauthenticated pending inventory. A manifest with execution or result fields but no summary is rejected rather than treated as a recoverable status.

Acceptance JSON maps T001, T002... to arrays of parent-defined checks. Supported checks:

    {"T001":[{"type":"json","path":"temp/result.json","equals":{"answer":42}}]}

file checks require a regular file and optionally sha256; json checks compare specified top-level values; absent checks confirm deletion. Check paths stay inside the initiating workspace and cannot traverse an existing symbolic link or junction. Controller acceptance is declarative only: workspace command checks are rejected because executing workspace-controlled code with controller authority is not a trust boundary. The runner rejects credential-shaped content in a persisted acceptance contract before it creates run state; use non-secret evidence checks. The parent must choose checks that establish the intended result: file existence alone is insufficient for semantic correctness. Checkpoint tokens identify this execution; they are not a security boundary against an intentionally malicious agent.

## Interruption and recovery

Typed provider account-quota errors such as usage_limit_exceeded are terminal for the invocation. The adapter accepts them from a typed `error`/`turn.failed` event or a structured `task_complete.error`; task text and tool output remain data. The runner records the provider error, closes the owned window, and skips both capacity backoff and the ordinary replacement-window budget; a later invocation may retry after the provider quota resets.

The launcher invokes the CLI once. It preserves failure evidence instead of blindly replaying a whole block. The controller independently rechecks every checkpoint and retries only remaining work, with a bounded attempt count (default two per block per controller) and backoff. Replacement windows use the same planned block and cannot exceed global concurrent capacity; verified tasks are omitted from their prompts. After a popup is confirmed, an unavailable launcher identity is not treated as an exit: only a result record bound to the current attempt token and launcher PID can prove the owned launcher exited; otherwise the lease and recovery files remain for reconciliation. An `exitUnprovenAt` marker in either the public block record or its attempt record blocks both `--resume-run` and `--verify-run`; an acceptance override cannot clear it. The issuing controller may make one identity-bound final-sweep recheck only after it durably records that marker. A later controller retains the evidence for explicit reconciliation instead of reopening or touching an unknown launcher.

Post-exit cleanup is an ordered controller transaction for the lease, registry, and launch artifacts. Its workspace journals begin at `pending`. Immediately before an arbitrary external cleanup hook, the controller-owned marker durably fences that phase as `inflight`; only after the hook returns can it become `done`. Recovery may continue a verified `pending` phase, or repair stale or missing workspace mirrors from a controller marker already at `done`. An `inflight` phase has no durable completion receipt, so `--resume-run` and `--verify-run` retain the evidence for manual reconciliation and never replay that cleanup automatically. A missing or mismatched controller marker also fails closed.

Every persisted protocol-2 attempt carries the same nonempty `leaseId` and controller-generated UUID `leaseInstanceId` in the summary and its on-disk attempt record. Resume, verification, and final cleanup reject a missing, partial, or mismatched binding rather than migrating an unsafe historical shape. If a reservation has committed but its acknowledgement is malformed, the controller uses only its in-process proof for rollback. A stale or failed proof rollback creates a blocked reconciliation record with the original UUID when available; it never retries or releases by public lease ID alone. Before any close-capable action, the current PID observation must also match the durable launcher process binding; a PID-file reuse or missing durable binding is retained for reconciliation.

If a task started but its output cannot be proven, automatic retry requires an explicit parent-defined policy:

    {"T002":{"retrySafe":true,"checks":[{"type":"json","path":"temp/result.json","equals":{"done":true}}]}}

retrySafe means repeating the operation cannot create an unintended duplicate effect; it is not a user approval switch. It defaults to false. Tasks with uncertain effects stay in the ledger as needs-reconciliation, and their dependants do not run. The parent investigates actual state and supplies meaningful verification; it must not mark arbitrary commands retry-safe to force progress. Exactly-once execution of arbitrary external effects cannot be guaranteed without an external idempotency mechanism.

A `started` checkpoint without `completed` is not automatic success, even if the output already satisfies the checks. Ordinary completion and recovery leave it in `needs-reconciliation`. After inspecting the effect, the parent may explicitly use `--verify-run` with meaningful checks to record a reconciled result only after every owned launcher and headless child has authenticated exit proof. `--verify-run` cannot clear an unresolved launcher or child marker, even with an acceptance override; that state requires explicit reconciliation first. Later recovery rechecks a reconciled result without executing the task again. Saved checkpoints must match the task, run, attempt token and allowed state, including when the standalone checkpoint file is missing.

--resume-run reuses the saved task inventory, acceptance checks and original workspace. It never calls the planner again. The controller stores a separate digest of the original request, task inventory, plan, block assignment, agent, mode and authorization under `CODEX_HOME/state/plugins/codex-tui-orchestrator/plans`; resume refuses a missing or changed binding before launching or closing a worker. At runtime, a live launcher is adopted only when PID, creation time, executable, and exact command line match. Durable/public state keeps a SHA-256 binding of that command line rather than the raw text; legacy durable identities containing raw command lines or lacking a valid binding fail closed. No replacement is opened while it survives. Final cleanup re-identifies a launcher from its controller-owned PID file before accepting a saved process identity. A dead controller's ownership is reclaimed under the coordinator mutex, and a second live controller is rejected. Run release checks both the recorded token and the current controller's PID, creation time, executable name and command-line binding; a worker that merely reads the token cannot call the release API on behalf of a live controller. Completed tasks are rechecked; successful finalized runs with a plan binding resume without opening any window. Historical runs without that binding cannot resume, but can still be rechecked with --verify-run. Recovery of protocol-1 runs is not supported; their original explicit acceptance checks can still be used with --verify-run. After a controller crash, the initiating agent invokes --resume-run; there is no background service that restarts controllers automatically.

## Acceptance-contract binding

`<runDir>/acceptance.json` lives in the workspace the execution windows can write to, so the contract itself needs integrity before it can establish anything about a task. At run start the controller records the SHA-256 of the canonical contract (object keys sorted, formatting ignored, `null`/`Infinity`/`-0` kept distinct) as `acceptance` in `manifest.json` and `summary.json`, and anchors the same digest under `CODEX_HOME/state/plugins/codex-tui-orchestrator/acceptance`. `--verify-run` and `--resume-run` compare the contract to that controller-side binding before touching task state. If the two workspace ledger bindings disagree or the controller binding is missing, verification and recovery refuse to choose an on-disk copy. The parent must inspect the contract and explicitly use `--allow-acceptance-change` to adopt or rebind it.

Deliberately replacing a contract — the parent narrowing or extending checks after inspecting an uncertain result — requires the explicit `--allow-acceptance-change` flag (place it after the run ID) or `ORCH_ACCEPTANCE_OVERRIDE=1`. The override prints a warning, rebinds the new digest in the controller state and both ledgers, and appends an `acceptanceRebound` entry (`from`, `to`, timestamp, generation, and the conflict when present) to the run history. Historical ledgers without a controller binding require this explicit adoption before verification.

The controller-side binding assumes that a worker can change its workspace but cannot gain authority from a session file, environment variable, or locally editable controller record. A headless child is strictly read-only and noninteractive. A write-capable task is routed to a visible Codex interaction with `on-request` approval; the plugin does not add a bypass or trusted-project override. Acceptance checks remain declarative and do not execute workspace-provided code. The narrower isolated-acceptance file-protocol property and its same-user native-process limitations are documented in [security boundaries](security-boundaries.md).

## Global coordination and process identity

Codex runs use an independent window coordinator across this Windows user session, including different workspaces. Its default directory is `CODEX_HOME/state/plugins/codex-tui-orchestrator/codex-coordinator`. A Windows named mutex serializes lease changes and is released on crashes. Workspaces keep their task records and checkpoints in their own temp directories. `ORCH_CONTROLLER_ROOT`, `ORCH_COORDINATOR_DIR`, and the direct API's explicit coordinator are advanced overrides; each must be outside the initiating workspace, a local non-UNC directory, and writable only by the current Windows user, `SYSTEM`, and `Administrators`. Physical path identity is checked even for a workspace that has not yet been created, including Windows short names and alternate UNC spellings. Resume and verification check a saved coordinator against the independently resolved current directory or an explicitly supplied matching coordinator before creating a file. Historical runs with a different locator require review and an explicit override; a workspace-local historical coordinator is rejected. If the workspace contains CODEX_HOME, select a narrower project workspace or an independently trusted controller root outside it. Drain active runs before upgrading from a version using the former HKCU locator: old and new versions have separate lease pools during a mixed-version interval.

A lease is held before launch and records owner and launcher identity. Capacity counts pending and active windows across runs. Busy resources wait without dropping tasks. Only resource/dependency waits and pre-existing global occupancy delay execution; overflow tasks never create extra windows. A live identity check uses PID, creation time, executable name, and the exact command line observed from the operating system. Durable coordinator records, leases, run-owner state, window registries, and process-snapshot caches retain only a SHA-256 command-line binding; legacy persisted identities with a raw command line or no valid binding are rejected. Close operations recheck identity and kill descendants deepest first; they do not kill the shared Windows Terminal host. Headless prompts travel over stdin. If credential-shaped text reaches a headless prompt, the original is held in a CurrentUser-DPAPI controller file and decrypted only for that stdin write; retained prompt and output artifacts use the public projection. This is defense in depth, not permission to put passwords, API keys, tokens, connection strings, or other secrets in prompts. The official interactive Codex CLI takes its initial prompt as a positional argument and has no supported stdin channel, so visible TUI execution refuses a credential-shaped prompt, title, or suffix before it writes launcher files or opens a child. Ordinary visible prompts remain subject to the normal same-user local inspection boundary.

## 双通道实时状态

TodoList（原始任务清单）保留 T001 等任务身份。Execution（执行块状态面板，也称 spawn 状态）显示每个块的模式、PID、尝试次数、等待原因和重试时间。块已启动不代表其中每个任务都已开始。

- started 检查点使任务进入 running；completed 进入 awaiting-verification；独立验收通过才显示 verified。
- 执行输出持续显示双状态。交互终端固定刷新面板，普通输出按状态变化追加。
- manifest.json 从规划开始保存清单；summary.json 是权威快照，events.jsonl 是带序号事件，goal.json 是派生镜像。文件都归当前工作区 temp/orchestrator/runs/<ID>。

~~~powershell
node scripts/status.mjs --workspace [WORKSPACE]\your-project --run-id <ID> --watch
node scripts/status.mjs --workspace [WORKSPACE]\your-project --run-id <ID> --watch --json
~~~

status.mjs 只读且不依赖 SDK，退出观察不会终止执行。JSONL（逐行 JSON 事件）用于接入宿主界面；重连先读最新快照再跟随事件，--after 指定已观察序号。默认每 250ms 观察检查点，系统和同步协调可能延迟显示，不承诺硬实时。

Codex 原生 TodoList/spawn 卡片属于宿主界面。本插件提供持续终端面板和状态事件；原生卡片需要宿主消费同一接口，不能仅靠技能文件注入。可以随时打开观察面板；选择下一次任务的执行模式不会重启当前任务。

恢复沿用原来的执行模式和任务身份。旧记录未声明模式时仍按 visible 恢复，不会因新默认值改变执行方式。

## Execution modes

`--exec`/`--headless` uses a durable hidden `codex exec --json` worker only for read-only work with `approval_policy="never"`. It passes the official `--ignore-rules` flag so user and project rule layers cannot turn the worker into a sandbox bypass. `--run` and bare requests start from `ORCH_EXEC_MODE`, then route to visible execution whenever the initiating policy may need approval. `--run-windows`/`--visible` explicitly selects visible TUI. Both modes use the same runner and leases. Workers wait for controller admission, then own their CLI child, logs and result. Controller loss does not lose the pipes or replay the block.

Each run saves executionMode. Legacy missing values mean visible. At runtime, worker adoption checks PID, start time, and the exact worker/configuration command line; its durable identity record uses only the command-line SHA-256 binding and rejects legacy raw identities. Ordinary and capacity failure budgets remain separate. Only unstarted or explicitly retry-safe tasks can be repeated. Readers ignore truncated final event lines; the next claimed writer repairs them. Invalid complete event records fail visibly. Stale goal mirrors rebuild from the validated summary.

## Runtime policy

Visible windows default to Windows Terminal (`ORCH_TUI=wt`). PowerShell remains the internal lifecycle-script interpreter. Explicit `ORCH_TUI=inactive` selects direct console creation with a non-activation request; neither path is certified universally interruption-free. Focus behavior and its measured limitations are documented in [inactive windows](inactive-windows.md).

Windows inherit the initiating directory; a restricted turn cannot select another working directory. Run ledgers and checkpoints stay under that workspace/temp; controller-owned launch files and bindings stay under `CODEX_HOME/state/plugins/codex-tui-orchestrator`. A relative `CODEX_HOME` is resolved from that child directory before it is passed on; ambiguous Windows rooted or drive-relative forms are rejected. A headless run successfully finalized by its controller removes its launch files, while an unfinished or failed run retains them for recovery. Codex-owned configuration and sessions remain under `CODEX_HOME`. Windows inherit the initiating approval policy. If approval is on-request, a normal `--run` uses visible interaction and explicit headless execution fails before starting a worker. A visible launch clears inherited extra writable roots, does not add a dangerous bypass or trust override, and refuses an active or unsafe user/project `.rules` layer before creating its launcher, before opening the terminal, and within its launcher immediately before calling Codex. This is a pre-launch check rather than a same-user filesystem lock: use visible mode only when no untrusted concurrent same-user process can alter the workspace configuration; use a separate account or stronger isolation for that threat. The official headless `--ignore-rules` option skips `.rules` files only from its User and Project layers; it does not suppress system-layer `.rules` or host-managed requirements or restrictions, and ordinary configuration precedence remains Codex-defined. Existing external host restrictions still apply. The Codex adapter inherits the initiating provider and credentials by default, including third-party providers, so it needs no OpenAI session of its own. The opt-in OpenAI HTTPS provider keeps the existing OpenAI login, uses HTTPS Responses and disables WebSocket probing. Network loss can still cause HTTPS retries. Windows PowerShell native argv escaping preserves JSON, quotes, Chinese and paths with spaces. CurrentUser-DPAPI is not a same-user process isolation boundary, and host-managed conversation/session records remain outside the plugin's cleanup and redaction authority.

## Regression commands

Regression and coverage commands are source-checkout maintainer procedures and are deliberately excluded from an installed artifact. Release validation runs the current serial source suite, a seal-verified distribution, and an isolated installation against the same candidate. For the opt-in calculated-capacity real-model acceptance, invoke the source harness by absolute path from the desired workspace and explicitly set `ORCH_LIVE_MODE=headless` or `ORCH_LIVE_MODE=visible`; it always uses the source orchestration entry and rejects an `ORCH_LIVE_ENTRY` override. Installed-artifact acceptance is separate and must verify the artifact seal. Historical result files are not evidence for a changed core version; retain newly generated run IDs and summaries.

## Operational flags and environment

`--clear-cache` removes the deterministic decomposition cache. `--selftest-close` opens a bounded self-test window and records `temp/selftest-close.json`; it is a diagnostic gate, not task execution. `ORCH_TASK_HINTS`, `ORCH_TASK_FOLD` and `ORCH_TASK_TAIL` provide optional JSON routing hints. `ORCH_STATUS_FORMAT=json` emits status events as JSON. `ORCH_OPENAI_BASE_URL` (legacy alias `ORCH_STEADY_RELAY_BASE_URL`) is the optional relay base URL for the opt-in OpenAI HTTPS provider; it must end in `/v1`, may use `http` only for loopback hosts, and cannot contain credentials, query parameters or fragments. `ORCH_PROVIDER` selects `inherit` (default) or `openai-https`. Neither selection collects telemetry.
